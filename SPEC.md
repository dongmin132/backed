# Backed — build spec

Backed is a prepaid-balance ledger for small shops that take customer money up front
(house tabs, class packs, stored value). PayPal is the only rail money moves on.
Every day the books are closed against PayPal's own records; anything PayPal shows
that the ledger cannot explain becomes a break. An AI investigator reads the evidence,
proposes the correcting journal entry, code validates it, and a second person approves it.

This file is the contract between the people (and agents) building it. If something
here is wrong, fix the spec in the same change.

## Non-negotiables

- Money is `long` cents, USD only. No floating point anywhere near money.
- The ledger is append-only double entry. Entries are never updated or deleted;
  mistakes are fixed by a new correcting entry dated the next business date.
- Every journal entry balances (sum of debits = sum of credits). Enforced in
  `JournalService` and by a deferred constraint trigger in the database.
- A customer balance can never go negative: `CHECK (balance_cents >= 0)` plus a
  conditional `UPDATE ... WHERE balance_cents >= ?` whose affected-row count is checked.
  Never read-then-write a balance in Java.
- Every PayPal write carries a deterministic `PayPal-Request-Id` that is stored
  before the call is made. A retry reuses the same id. A new id is only minted for
  a new business intent.
- A timeout is not a failure. Outcome unknown is its own state (`IN_DOUBT`) and is
  resolved by asking PayPal, never by guessing.
- No external call inside a database transaction that holds a row lock.
- The AI never produces an amount that is posted as-is. It picks a treatment and
  cites evidence; code derives amounts from PayPal data and validates the draft.
- Maker and checker are different users. The server rejects self-approval.
- No secrets in the repo. `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`,
  `ANTHROPIC_API_KEY` come from the environment (a local `.env` is git-ignored).

## Stack

Java 21, Spring Boot 4.1 (webmvc, jdbc with `JdbcClient`, security, thymeleaf, flyway,
validation), PostgreSQL. No JPA. htmx from a pinned CDN URL for small page updates.
PayPal Java Server SDK `com.paypal.sdk:paypal-server-sdk:2.4.0` (generated by APIMatic)
for Orders and Payments. Anthropic Java SDK for the investigator.

Database: an embedded real PostgreSQL (`io.zonky.test:embedded-postgres`) starts
automatically when `BACKED_DB_URL` is not set, so `./gradlew bootRun` works with zero
setup and tests run against real PostgreSQL without Docker. When `BACKED_DB_URL`,
`BACKED_DB_USER`, `BACKED_DB_PASSWORD` are set, that database is used instead.

## Chart of accounts

| code | type | meaning |
|---|---|---|
| `PAYPAL_CASH` | asset | what PayPal holds for the shop: capture net amounts minus refunds |
| `IN_DOUBT_RECEIVABLE` | asset | top-ups sent to PayPal whose outcome is unknown |
| `CUSTOMER_PREPAID` | liability | control account; the sum of all customer balances |
| `SUSPENSE_IN_DOUBT` | liability | other side of `IN_DOUBT_RECEIVABLE` |
| `CASHOUT_CLEARING` | liability | balance already taken from a customer, refund leg in flight |
| `SALES_REVENUE` | income | recognised when a balance is spent |
| `PAYPAL_FEES` | expense | PayPal fee on captures |
| `GOODWILL_EXPENSE` | expense | refunds given as compensation, not as balance returned |

`customer_balances` is the subledger of `CUSTOMER_PREPAID`. Lines on `CUSTOMER_PREPAID`
always carry `customer_id`.

## Postings

G = gross captured, F = PayPal fee, all in cents.

| event | entry | balance row |
|---|---|---|
| top-up captured | Dr `PAYPAL_CASH` G−F, Dr `PAYPAL_FEES` F, Cr `CUSTOMER_PREPAID` G | `+G` |
| top-up outcome unknown | Dr `IN_DOUBT_RECEIVABLE` G, Cr `SUSPENSE_IN_DOUBT` G | none |
| in-doubt resolved (either way) | Dr `SUSPENSE_IN_DOUBT` G, Cr `IN_DOUBT_RECEIVABLE` G, then the captured entry if it was captured | `+G` if captured |
| spend S | Dr `CUSTOMER_PREPAID` S, Cr `SALES_REVENUE` S | `−S` conditional |
| cash-out requested X | Dr `CUSTOMER_PREPAID` X, Cr `CASHOUT_CLEARING` X | `−X` conditional |
| cash-out leg refunded R | Dr `CASHOUT_CLEARING` R, Cr `PAYPAL_CASH` R (when PayPal reports a returned fee F on the refund with net + F = R: Cr `PAYPAL_CASH` net, Cr `PAYPAL_FEES` F) | none |
| cash-out leg failed for good R | Dr `CASHOUT_CLEARING` R, Cr `CUSTOMER_PREPAID` R | `+R` |
| off-book refund = balance returned R | Dr `CUSTOMER_PREPAID` R, Cr `PAYPAL_CASH` R | `−R` conditional |
| off-book refund = goodwill R | Dr `GOODWILL_EXPENSE` R, Cr `PAYPAL_CASH` R | none |
| off-book refund = reversal of a capture the ledger never credited R | Dr `PAYPAL_CASH` R (the unbooked capture, net of fee as PayPal reports), Dr `PAYPAL_FEES`, Cr `PAYPAL_CASH` R ... see `investigate` for the exact lines | none |

Refund fee handling: use the amounts PayPal returns (`seller_payable_breakdown`) when
present; otherwise treat the refund as reducing `PAYPAL_CASH` by the gross refund amount.

## State machines

Top-up: `CREATED → CAPTURED | DECLINED | IN_DOUBT`, `IN_DOUBT → CAPTURED | NOT_CAPTURED`.
While a customer has an `IN_DOUBT` top-up, a new top-up for that customer is refused
(the guard that stops the classic double charge).
Top-up details (module `topup`): the request id is `topup-<id>`. A 4xx, or a 5xx / connection
refused on the first attempt, ends in `DECLINED` with nothing charged (the single request did not
take effect, so the customer may start a new top-up). Resolving re-sends the original request with the
same request id: PayPal returns the original capture if it made one, or makes it now if the first
request never arrived; a 4xx on the re-send means `NOT_CAPTURED`; a 5xx or timeout leaves it
`IN_DOUBT`. A `CREATED` row untouched for 2 minutes (the app stopped mid-call) is resolved the same way.
Amounts are $1.00 to $10,000.00. For reads (GET order, GET capture) a timeout counts as unavailable,
and 408, 409 and 429 count as unavailable for every call. Live check of these assumptions:
`./gradlew bootRun --args='--spring.profiles.active=sandbox-check'` (needs credentials).

Cash-out: `REQUESTED → SETTLED | PARTIALLY_SETTLED | COMPENSATED`.
Cash-out leg: `PENDING → DONE | IN_DOUBT | FAILED`, `IN_DOUBT → DONE | FAILED`.
The balance debit and the `PENDING` leg rows are written in one transaction (this is
the outbox). A scheduler picks up `PENDING` and `IN_DOUBT` legs with
`FOR UPDATE SKIP LOCKED`-style claiming, calls PayPal outside the transaction, and
records the result. Resuming never re-sends a leg that is `DONE`. Legs are allocated
newest capture first; a leg never exceeds what is still refundable on its capture.
A run claims a leg by setting `cashout_legs.claimed_until` (added by `V30`, the cash-out
module's migration) and counting the attempt; results are recorded only if the attempt count
still matches. A 5xx retries a `PENDING` leg up to `backed.cashout.max-attempts` (default 5)
and then fails and compensates it; an `IN_DOUBT` leg is only ever settled by PayPal's answer
to the same request id, never failed for lack of one.

Error classification for every PayPal call:

| PayPal says | meaning | action |
|---|---|---|
| 2xx | done | record |
| 4xx business error | will never succeed | no retry, fail the step |
| 5xx / connection refused | not done | retry later with the same request id |
| read timeout / connection dropped mid-response | unknown | `IN_DOUBT`, resolve by re-sending the same request id |

## Day close

For the current business date:

1. Try to resolve every `IN_DOUBT` top-up and cash-out leg by asking PayPal.
2. For every top-up that has a PayPal order id, GET the order and compare its captures
   and refunds with the ledger. A refund PayPal has that the ledger has no leg or
   resolved break for is a break (`UNBOOKED_REFUND`). A capture PayPal has that the
   ledger has not credited is a break (`UNBOOKED_CAPTURE`).
3. Check: every entry balances; sum of `customer_balances` = `CUSTOMER_PREPAID` balance;
   ledger `PAYPAL_CASH` = cash derived from PayPal's records. The difference in the
   last check is the "unexplained" amount.
4. The day is `CLOSED` only if there are no open breaks, nothing `IN_DOUBT`, and
   unexplained = 0. Otherwise it is `BROKEN` and lists the breaks.

Transaction Search is not used (it lags by hours in sandbox). The close reads orders,
captures and refunds directly.

Details fixed by the close module (`DayCloseService`):

- Every PayPal read happens before anything is written and outside any transaction. If one
  fails, the run is stored as `BROKEN` with the reason and no break is written.
- The ledger side (top-ups, legs, resolved breaks, the three check figures) is read in one
  `REPEATABLE READ` snapshot after PayPal was read.
- Orders come from `topups.paypal_order_id`, plus the orders of captures named by
  `PAYMENT.CAPTURE.*` webhooks that no top-up points to. A webhook capture PayPal answers 404
  for (for example from the webhook simulator) is noted and ignored.
- PayPal-derived cash = sum of capture net amounts (`COMPLETED`, `PARTIALLY_REFUNDED`,
  `REFUNDED`; net, else gross minus fee, else gross) minus `COMPLETED` refunds (net from the
  breakdown when present, else gross).
- No break is raised for a capture whose top-up is still `CREATED` or `IN_DOUBT`, or for a
  refund that matches a `PENDING` or `IN_DOUBT` leg (same refund id, or same capture and
  amount); those are left to their resolvers and the day stays `BROKEN` while anything is in doubt.
- `CLOSED` additionally requires the balance and subledger checks to pass.
- Breaks are keyed by (kind, PayPal id), so re-running never duplicates one; a `RESOLVED` break
  explains its PayPal object on later runs.
- `POST /close/advance` moves the business date only if the newest run for the current date is
  `CLOSED` and the journal has the same number of entries as when that run read it.

## Webhooks

`POST /webhooks/paypal` (public, no CSRF) stores the event keyed by its `id` with
`insert ... on conflict do nothing` and processes it in the same transaction, so a repeated or
concurrent delivery is answered 200 `duplicate` without processing. Processing never posts to
the journal; it only reports whether the ledger knows the capture or refund. Signature
verification through PayPal's verify-webhook-signature endpoint is off by default; set
`backed.webhooks.verify-signature=true` and `backed.paypal.webhook-id` (or `PAYPAL_WEBHOOK_ID`)
to turn it on. Staff see received events at `/close/webhooks` (not under `/webhooks/**`, which
is public).

## Investigator

Input per break: the PayPal refund or capture as returned by PayPal (including the
note to payer), the customer's recent ledger history, the customer's messages, and
other open breaks for the same customer. Output (strict JSON): treatment
(`BALANCE_RETURNED`, `GOODWILL`, `DUPLICATE_REVERSAL`, `NEEDS_HUMAN`), the evidence
quotes it relied on, the alternative it rejected and why, and a short customer note.

Code then builds the journal draft from the treatment and PayPal's amounts and
validates: entry balances; amounts equal PayPal's; only allowed accounts; every
evidence quote is a verbatim substring of the input; the customer balance would not
go negative. A draft that fails validation is shown as rejected with the reason.
Approval posts the entry dated the next business date with `created_by` = maker and
`approved_by` = checker, then the close is re-run.

## Users (demo, in memory)

`clerk` (role CLERK: counter), `maker` (role MAKER: runs close, requests proposals),
`checker` (role CHECKER: approves). Password for all: `demo`. Customers do not log in;
each has a private link `/c/{token}`.

## Demo faults

`/admin/faults` (MAKER) exposes clearly labelled switches used in the demo and tests:
drop the response of the next capture after PayPal has accepted it; fail the next
refund with a 5xx; issue a refund directly at PayPal outside the ledger (stands in
for a refund made by hand in the PayPal dashboard).

## Tests that must exist

- 20 threads spend $1 from a $10 balance: exactly 10 succeed, balance ends at 0,
  ledger still balances.
- Capture accepted by PayPal but response lost: one capture, same request id on the
  re-send, customer credited once.
- New top-up refused while one is `IN_DOUBT`.
- Cash-out across three captures where leg 2 fails with 5xx: on resume only leg 2 is
  sent again, with its original request id.
- 4xx on a refund: zero retries, leg `FAILED`, balance compensated.
- Same webhook delivered twice: processed once.
- Self-approval rejected; unbalanced or mis-amounted draft rejected.
- Close goes `BROKEN` on an off-book refund and `CLOSED` after the approved correction.

## Foundation conventions

These are fixed by the foundation commit; module code relies on them.

- Schema: the whole schema is `V1__schema.sql`; `V2__seed.sql` loads accounts, the business
  date and three demo customers. Modules add no migrations, except within the version range
  their brief assigns (cash-out: `V30__cashout_leg_claim.sql`). JSON columns (`breaks.evidence`,
  `proposals.ai_output`, `proposals.draft`, `day_closes.summary`, `webhook_events.payload`)
  are `text` holding JSON.
- The journal is append-only in the database too: UPDATE and DELETE on `journal_entries` and
  `journal_lines` raise an error.
- At most one journal entry per `(kind, ref_type, ref_id)`; a second posting for the same
  business object fails with a duplicate key. Use the object's own id as `ref_id`.
- At most one unresolved top-up (`CREATED` or `IN_DOUBT`) per customer, enforced by a partial
  unique index. Inserting a second one fails with a duplicate key: that is the refusal.
- Entries that touch `CUSTOMER_PREPAID` are posted with `JournalService.postAndApply`, which
  applies the customer lines to `customer_balances` (conditional debit) in the same transaction.
- Actor names: controllers pass `Actors.of(principal)`; schedulers, webhooks and customers use
  `Actors.SCHEDULER`, `Actors.WEBHOOK`, `Actors.customer(id)`. Services take the actor as a
  `String` parameter.
- `@Scheduled` methods run only when `backed.scheduling.enabled` is true (default). Tests set it
  to false.
- PayPal wiring: the real SDK adapter is registered only when `backed.paypal.mode=sandbox`
  (default) and is exposed wrapped in `FaultInjectingPayPalGateway`. Tests set
  `backed.paypal.mode=fake` and get `FakePayPalGateway` (src/test) behind the same wrapper.
- Tests extend `dev.backed.support.AbstractDbTest`: one Spring context, every table truncated and
  the seed reloaded before each test, fake PayPal and fault switch reset.
- Customer page actions (`POST /c/{token}/topup`, `/cashout`) redirect back to `/c/{token}` with a
  flash attribute `notice` (success) or `error`.
